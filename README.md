# هستهٔ اولیهٔ بلیط‌چی — ۰.۱.۰

این بسته یک هستهٔ دامنهٔ قابل اجرا و آزمون است؛ سایت کامل یا نسخهٔ آمادهٔ فروش عمومی نیست. چون درایو پروژه در محیط اجرا در دسترس نبود، مستقل ساخته شده است و هیچ تغییری در مخزن E انجام نشده است.

## مبنای محصول

- پکیج اول: سینما.
- منطقهٔ اولیه: شهرستان نوشهر.
- نام اپراتور، سینما، دامنه، لوگو و رنگ: خالی.
- سامانهٔ بیرونی و درگاه واقعی: هنوز انتخاب نشده‌اند.
- Python و SQLite برای این بستهٔ مستقل و بدون وابستگی انتخاب شده‌اند؛ تصمیم قطعی فناوری وب یا زیرساخت عملیاتی نیستند.

## اجرا

Python نسخهٔ ۳.۱۲ یا بالاتر لازم است. اجرای هسته و آزمون‌ها وابستگی خارجی ندارد. از داخل پوشهٔ بسته اجرا کنید:

~~~text
python -m unittest discover -s tests -v
python -m bilitchi init --db data/local.db
python -m bilitchi demo --db data/demo.db
python -m bilitchi inventory --db data/demo.db --show-id sample-show
~~~

فرمان demo فقط با دیتابیس جدید اجرا می‌شود و دادهٔ موجود را بازنشانی نمی‌کند. مبلغ، شناسهٔ پرداخت و خریدار آزمایشی‌اند؛ هیچ پولی جابه‌جا نمی‌شود. نام تجاری نمونه نیز خالی است.

## امکانات پیاده‌شده

- مرکز، کانال فروش، سانس و صندلی با شناسه‌های مستقل.
- رزرو گروهی کامل یا رد کامل در یک تراکنش.
- جلوگیری از تصاحب هم‌زمان صندلی در دیتابیس مرجع داخلی.
- انقضا، آزادسازی و یک تمدید محدود با زمان مرجع.
- کلید عملیات تک‌اثری با تشخیص تغییر محتوای درخواست.
- سفارش تک‌مرکزی و ثبت مبلغ و نرخ کمیسیون هنگام سفارش.
- ثبت نتیجهٔ تأییدشدهٔ درگاه از طریق ورودی مورد اعتماد.
- پرداخت نامشخص، چند پرداخت موفق و وجه اضافه.
- تصاحب مجدد ظرفیت پس از پرداخت دیرهنگام با شناسهٔ رزرو جدید.
- صدور بلیط و ثبت سهم مرکز در یک تراکنش با فروش.
- کنترل مصرف دوباره و رقابت میان مصرف و لغو.
- لغو جزئی با بازپرداخت کامل همان بلیط و اصلاح حساب مرکز.
- ثبت دستی پرداخت بازپرداخت و رسید یکتا.
- ماندهٔ مرکز، موعد آزمایشی تسویه و ثبت دستی تسویه.
- موجودی کانال مستقل بیرونی بدون ثبت درآمد برای اپراتور.
- صف بررسی با مسئول عمومی اپراتور و موعد اولیه.
- ثبت رخداد ماندگار و گزارش عملیات حساس اصلی.

## مرز امنیت و استفاده

کلاس Core یک API اینترنتی نیست. ورودی‌های actor، channel و allowed_show_id باید توسط لایهٔ معتبر احراز هویت و مجوزدهی تعیین شوند؛ از درخواست مستقیم کاربر قابل اعتماد نیستند. متد record_payment فقط پس از استعلام معتبر درگاه فراخوانی می‌شود. این بسته خودش با درگاه صحبت نمی‌کند.

رویدادها و خواندن سفارش برای مصرف داخلی‌اند؛ پیش از ارائه به مشتری یا کانال بیرونی باید بر اساس دسترسی فیلتر شوند. فایل تنظیمات نمونه مستند پیکربندی است و هنوز به راه‌اندازی محصول متصل نشده است؛ production_enabled=false به‌تنهایی دروازهٔ امنیتی نیست.

شناسهٔ بلیط QR امضاشده نیست. QR، احراز هویت، پنل و وب‌سرویس عمومی در این بسته وجود ندارند.

## فرض‌های آزمایشی

- پول: ریال صحیح؛ قیمت همهٔ صندلی‌های هر سانس یکسان.
- کمیسیون پیش‌فرض نمونه: ۱۰٪ و هنگام سفارش ثابت می‌شود.
- سهم مرکز به بلیط‌ها با تخصیص باقی‌ماندهٔ قطعی تقسیم می‌شود.
- موعد آزمایشی تسویه: سه روز پس از شروع سانس، صرفاً برای اثبات حساب؛ جایگزین قاعدهٔ نهایی پایان برنامه و مهلت لغو نیست.
- لغو فقط توسط لایهٔ مدیریتی مورد اعتماد، با بازپرداخت کامل بلیط مصرف‌نشده است؛ موتور قوانین لغو هنوز وجود ندارد.
- پنجرهٔ زمانی کنترل ورود هنوز اعمال نمی‌شود؛ محدودیت فعلی مربوط به سانس مجاز و وضعیت مصرف است.
- کنترل هم‌زمانی SQLite با قفل نویسنده اجرا می‌شود؛ هیچ ادعای تحمل ۵۰ رزرو در ثانیه یا بار عملیاتی سند محصول نشده است.

## آنچه هنوز آماده نیست

پنل و سایت فارسی، ورود پیامکی و نقش‌ها، درگاه و پیامک واقعی، اتصال مرجع بیرونی، امضای QR، محدودیت نرخ و ربات، مالیات و تخفیف، نقشهٔ بصری سالن، قواعد لغو، بازپرداخت خودکار، جریان تأیید و رزرو مبلغ تسویه پیش از انتقال بانکی، استعلام زمان‌بندی‌شده، تشدید و واگذاری پرونده، ارسال و تأیید دریافت رخداد، نصب تجاری و مجوز، مهاجرت نسخه‌دار و بازیابی عملیاتی هنوز باید ساخته شوند.

ثبت تسویه مانع ثبت مضاعف مانده در همین دیتابیس می‌شود، اما از دو انتقال وجه بیرون از سامانه جلوگیری نمی‌کند. جریان آماده‌سازی و تخصیص تسویه پیش از انتقال واقعی باید پیش از بهره‌برداری اضافه شود.

پیش از ادغام، ساختار و راهنمای مخزن اصلی باید بررسی شوند. این بسته در مسیر جایگزین ساخته شده و چیزی در پروژهٔ اصلی بازنویسی نمی‌کند. فناوری نهایی، مدل استقرار و مرجع موجودی پس از دسترسی به مخزن تعیین می‌شوند. قواعد و آزمون‌های این بسته مبنای مرحلهٔ بعد هستند.
