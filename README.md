# بلیط‌چی

[راهنمای اسناد](docs/README.md) · [نگاشت دامنه و پذیرش](docs/blueprint/traceability.md) · [تصمیم‌های فنی](docs/architecture/decisions.md)

پکیج اول سینما و بازار اولیه نوشهر است. نام اپراتور، سینما، دامنه، برند و ارائه‌دهندگان فعلاً خالی‌اند. فناوری عملیاتی هنوز پذیرفته نشده است؛ A04 و A06 برای گزینه‌های سبک‌تر در حال بازبینی‌اند.

## هستهٔ مرجع ۰.۲.۰

این کد کتابخانهٔ دامنهٔ آزمایشی Python/SQLite است، نه سایت کامل، API عمومی یا محصول آمادهٔ فروش. نمونه برای بررسی رفتار و آزمون‌ها نگهداری می‌شود؛ انتخاب stack عملیاتی را تحمیل نمی‌کند.

### اجرا

Python 3.12 یا بالاتر، بدون وابستگی خارجی برای هسته و آزمون‌ها:

~~~text
python -m unittest discover -s tests -v
python -m bilitchi init --db data/local-v2.db
python -m bilitchi demo --db data/demo-v2.db
python -m bilitchi inventory --db data/demo-v2.db --show-id sample-show
python tools/check_docs.py
~~~

demo نیازمند دیتابیس جدید است، دادهٔ موجود را بازنشانی نمی‌کند و هیچ پولی جابه‌جا نمی‌کند. نام‌های تجاری نمونه خالی‌اند.

### سازگاری نسخهٔ ۰.۲.۰

نسخهٔ مرجع ۰.۲.۰ عمداً API و schema جدید دارد:

- add_show به ends_at نیاز دارد؛ cancellation_deadline_at اختیاری و پیش‌فرض برابر پایان است.
- release، extend و create_order به buyer معتبر به‌صورت keyword نیاز دارند.
- redeem به key نیاز دارد تا replay همان پذیرش نتیجهٔ قبلی را بدهد.
- کلید عملیات به channel، principal و command محدود است و رد قطعی کسب‌وکاری ذخیره می‌شود.
- initialize دیتابیس مرجع قدیمی را با خطای reference_schema_upgrade_required رد می‌کند؛ آن را حذف، بازنویسی یا با حدس پایان برنامه ارتقا نمی‌دهد.
- برای نمونهٔ تازه، مسیر دیتابیس جدید بدهید. دیتابیس قدیمی دارای داده را پاک نکنید؛ انتقال واقعی نیازمند نگاشت صریح، backup و ابزار آزموده است و در این نمونه ساخته نشده.

### رفتار موجود

رزرو گروهی اتمیک، سقف یک رزرو فعال برای buyer در هر سانس، تمدید محدود، انقضا، سفارش تک‌مرکزی، ثبت نتیجهٔ پرداخت مورد اعتماد، تصاحب مجدد دیرهنگام، بلیط، مصرف و لغو جزئی، وجه اضافه و بازپرداخت دستی، حساب مرکز و ثبت دستی تسویه، فروش موجودی کانال مستقل و رویدادهای ماندگار.

اصلاحات بازبینی:

- لغو پیش‌سررسید، ماندهٔ قابل تسویهٔ منفی کاذب نمی‌سازد.
- تکرار خطای قطعی همان نتیجه را می‌دهد؛ قصد تازه کلید تازه می‌خواهد.
- سهم مرکز به ریال صحیح پایین گرد می‌شود و باقی‌ماندهٔ کسری به اپراتور می‌رسد؛ این سیاست آزمایشی تا پذیرش D06 است.
- موجودی فقط خوانده می‌شود؛ sweep_expired یا فرمان نوشتنی پاک‌سازی می‌کند.
- مالکیت buyer در همان کانال برای تغییر و سفارش رزرو بررسی می‌شود.
- موعد تسویه max پایان برنامه و مهلت لغو + settlement_delay_seconds است؛ تأخیر پیش‌فرض آزمایشی سه روز.
- redeem با همان actor و key پاسخ موفق قبلی را replay می‌کند.

### مرزهای اعتماد

Core API اینترنتی نیست. actor، buyer، channel و allowed_show_id باید از لایهٔ احراز هویت معتبر بیایند، نه از پارامتر دلخواه خریدار. record_payment فقط از adapter مورد اعتماد پس از استعلام معتبر provider فراخوانی می‌شود؛ کد خودش به درگاه وصل نمی‌شود.

متدهای order، events و review_queue داخلی‌اند و برای عرضهٔ عمومی نیازمند مجوز و فیلتر هستند. احراز هویت، نشست، MFA، rate limit و CAPTCHA در این نمونه وجود ندارند. تنظیم production_enabled=false تنها مستند پیکربندی است، نه لایهٔ امنیتی.

QR امضاشده، پنجرهٔ زمانی پذیرش، maker-checker، آماده‌سازی و تخصیص تسویه پیش از انتقال، مالیات، تخفیف، استعلام زمان‌بندی‌شده، provider واقعی، پنل، وب، upgrade و backup عملیاتی هنوز پیاده نشده‌اند. وجود اسناد یا آزمون‌های مرجع، Wهای محصول عملیاتی را نمی‌بندد.

هم‌زمانی SQLite با قفل نویسنده کنترل می‌شود؛ معیار کارایی یا correctness پیاده‌سازی PostgreSQL با آن اثبات نشده است.
