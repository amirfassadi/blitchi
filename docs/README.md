# راهنمای مستندات بلیط‌چی

وضعیت: بستهٔ تصمیم‌گیری معماری، آمادهٔ بررسی مالک محصول. تاریخ: ۲۰۲۶-۱۰-۲۷.

۱. [سند محصول](product/product-spec.md): چه چیزی می‌سازیم و محدودهٔ انتشار اول.
۲. [پیشنهاد معماری](architecture/overview.md): دلیل انتخاب دیتابیس، بک‌اند و فرانت‌اند.
۳. [دفتر تصمیم‌های فنی](architecture/decisions.md): انتخاب‌ها و وضعیت تأیید هرکدام.
۴. [مدل داده و قواعد صحت](architecture/data-model.md).
۵. [بک‌اند، API و اتصال‌ها](architecture/backend-api.md).
۶. [فرانت‌اند و مسیرهای کاربر](architecture/frontend.md).
۷. [استقرار، امنیت و عملیات](architecture/operations.md).
۸. [طرح مرحله‌بندی اجرا](architecture/execution-plan.md): پیش‌نویس مقدماتی بلوپرینت؛ پس از تأیید معماری جزئی و تثبیت می‌شود.
۹. [وضعیت کد فعلی](implementation-status.md): نمونهٔ مرجع ۰.۱.۰؛ هنوز محصول عملیاتی نیست.

## مرجع و ترتیب تغییر

- دامنهٔ قابلیت‌ها: فقط جدول ۱۸.۱ سند محصول. توضیحات بخش‌های دیگر آن را بزرگ‌تر نمی‌کنند.
- تصمیم‌های کسب‌وکار: فقط D01 تا D17 در بخش ۲۳.۱ سند محصول.
- تصمیم‌های معماری: فقط A01 تا A12 در دفتر فنی. این تصمیم‌ها جای Dها را نمی‌گیرند.
- جزئیات داده، API و عملیات باید با تصمیم‌های پذیرفته‌شده سازگار باشند.
- نقشهٔ اجرا از دامنه و تصمیم‌های پذیرفته‌شده مشتق می‌شود و خودش مجوز تغییر آن‌ها نیست.
- پیشنهادهای فعلی معماری هنوز تأییدشده نیستند؛ نوشتن یا پوش‌کردن سند به معنی پذیرش انتخاب‌ها نیست.

## قاعدهٔ جلوگیری از انحراف

هر تغییر دامنه ابتدا جدول ۱۸.۱ و تصمیم D مربوط را اصلاح می‌کند. تغییر فناوری یا مرز ماژول ابتدا تصمیم A مربوط را با دلیل، جایگزین‌ها و اثر مهاجرت اصلاح می‌کند. سپس مدل داده، قراردادها، برنامهٔ اجرا و آزمون‌ها به‌روز می‌شوند. تغییر ضروری امنیتی باید مستند شود و با اصلاح فوری و ثبت اثر ادامه یابد؛ این قاعده مانع رفع اختلال ضروری نیست.

برای هر کار توسعه، پیوند دامنه، تصمیم وابسته، خروجی، آزمون پذیرش و وضعیت لازم است. عنوان «تکمیل همهٔ امکانات» جای تعریف کار را نمی‌گیرد.
