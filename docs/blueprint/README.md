# بلوپرینت اجرا — نسخهٔ پیش‌نویس ۰.۱

تاریخ: ۲۰۲۶-۱۰-۲۷. وضعیت: قابل بررسی؛ معماری هنوز پیشنهادی است.

این بسته جزئیات اجرای طرح مرحله‌بندی را اضافه می‌کند. تهیه و ثبت آن به معنی تأیید فناوری‌ها یا آغاز توسعهٔ عملیاتی نیست. کارهای مستقل از فناوری پیش می‌روند و انتخاب‌های اصلی تا دریافت نظر مالک محصول نهایی معرفی نمی‌شوند.

## مرجع‌ها

- دامنه: [جدول ۱۸.۱ سند محصول](../product/product-spec.md).
- تصمیم‌های محصول: بخش ۲۳.۱ همان سند.
- تصمیم‌های فنی: [A01 تا A23](../architecture/decisions.md).
- ترتیب مراحل: [طرح مرحله‌بندی B00 تا B10](../architecture/execution-plan.md).
- تنها فهرست وضعیت کارهای بلوپرینت: [کارها](work-items.md).
- شواهد لازم: [ماتریس پذیرش](acceptance.md).
- ردیابی کامل: [نگاشت دامنه و سناریو](traceability.md).
- رفتار: [فرمان‌ها و وضعیت‌ها](../contracts/state-transitions.md).
- دسترسی: [ماتریس مجوز](../contracts/permissions.md).

## ترتیب کار

۱. نظر مالک محصول روی انتخاب‌های اصلی ثبت و تصمیم مرتبط به‌روز شود.
۲. قرارداد داده و رفتار مسیر «رزرو تا بلیط» بازبینی و تثبیت شود.
۳. اسکلت عملیاتی با تصمیم‌های پذیرفته‌شده ساخته شود.
۴. مسیر عمودی با درگاه و مرجع آزمایشی تکمیل و روی دیتابیس واقعی آزموده شود.
۵. پنل‌ها، مالی، اتصال واقعی و عملیات تکمیل شوند.
۶. پیش از فروش عمومی، پایلوت و معیارهای پذیرش عبور داده شوند.

هر تصمیم برای مرحلهٔ مربوط دروازه است؛ نامعلوم‌بودن مرکز واقعی جلوی مدل‌سازی با شناسه و نام خالی را نمی‌گیرد، اما فروش واقعی بدون مرکز و قرارداد معتبر انجام نمی‌شود.

## قواعد کار

- نام مشتری، اپراتور، سینما، دامنه و ارائه‌دهندگان تا دستور جدید خالی‌اند.
- هر کار شناسه، تصمیم وابسته، خروجی قابل بررسی و آزمون دارد.
- هیچ کار به دلیل وجود توضیح در سند، انجام‌شده محسوب نمی‌شود.
- اسناد قرارداد فعلاً طرح‌اند؛ OpenAPI و schema اجرایی نهایی پس از پذیرش معماری تولید می‌شوند.
- نمونهٔ SQLite فعلی برای اثبات الگوریتم عملیاتی PostgreSQL کافی نیست.
- خروج از دامنه ابتدا تصمیم و دامنه را تغییر می‌دهد، سپس کد.
- اجرای خودکار و پس‌زمینهٔ این گفتگو تعریف نشده است؛ ادامهٔ کار در همین روند همکاری انجام می‌شود.
