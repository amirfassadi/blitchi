# راهنمای بررسی اسناد

برای بررسی لازم نیست همهٔ سند محصول را از ابتدا بخوانی.

## ترتیب پیشنهادی

۱. [خلاصهٔ معماری](architecture/overview.md): آیا ترکیب دیتابیس، بک‌اند، فرانت‌اند و تحویل مناسب است؟
۲. [تصمیم‌های فنی](architecture/decisions.md): هر مورد را می‌توان پذیرفت یا جایگزین کرد.
۳. جدول ۱۸.۱ [سند محصول](product/product-spec.md): آیا چیزی اضافه یا کم است؟
۴. [کارهای بلوپرینت](blueprint/work-items.md): ترتیب و خروجی مرحله‌ها روشن است؟
۵. [ماتریس پذیرش](blueprint/acceptance.md): چه شواهدی برای تحویل لازم است؟

## روش دادن نظر

می‌توانی همین‌جا به شناسه اشاره کنی؛ مثلاً «A04 را ساده‌تر کنیم»، «W013 اولویت بیشتری دارد» یا «D15 را دستی شروع کنیم». لازم نیست خودت GitHub را ویرایش کنی. نظر را در سند مربوط ثبت می‌کنیم و اثرش روی دامنه، قرارداد و برنامه بررسی می‌شود.

## چه چیزی هنوز نهایی نیست؟

فناوری‌ها، مرجع موجودی واقعی، provider پرداخت و پیامک، قواعد تخصصی مالی، روش اضطراری و جزئیات مجوز تجاری. پکیج سینما و بازار اولیهٔ نوشهر مشخص شده‌اند. نام‌ها عمداً خالی مانده‌اند.

## پذیرش و تغییر

پذیرش یک تصمیم فقط همان شناسه یا گروه صریح را می‌بندد. گفتن «ادامه بده» به‌تنهایی تأیید همهٔ تصمیم‌های باز یا نتایج آزمون انجام‌نشده نیست. پس از تأیید، متن تصمیم با تاریخ و دلیل ثبت می‌شود؛ اسناد هم‌پوشان به آن ارجاع می‌دهند.
