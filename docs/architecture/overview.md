# پیشنهاد معماری و فناوری

وضعیت: پیشنهادی برای توافق؛ نه تصمیم نهایی و نه پیاده‌سازی‌شده.

## زمینه و هدف

شروع با پکیج سینما در شهرستان نوشهر است. نام مشتری، اپراتور، سینما، دامنه و تأمین‌کننده فعلاً خالی می‌ماند. هر مشتری یک نصب مستقل و دیتابیس جدا دارد. ظرفیت ممکن است با فروشندگان و گیشه مشترک باشد.

معماری باید نصب قابل تحویل، شخصی‌سازی تنظیماتی، صحت مالی، جلوگیری از فروش تکراری و افزودن پکیج را پوشش دهد. کد Python و SQLite فعلی نمونهٔ رفتار است؛ انتقال قواعد و آزمون‌ها به نسخهٔ عملیاتی لازم است و کپی مستقیم دیتابیس نمونه مسیر مهاجرت مشتری واقعی نیست.

## بازبینی پس از بررسی ریپو

A04 و A06 دوباره باز شده‌اند. برای نسخهٔ اول، قالب Django با تعامل محدود و صف PostgreSQL گزینه‌های سبک‌تر جدی هستند. [مقایسهٔ گزینه‌ها](decision-options.md) و W035 مرجع تعیین تکلیف‌اند؛ Next.js و RabbitMQ انتخاب نهایی نیستند. جدول و نمودار زیر معماری کامل گزینهٔ قبلی را توضیح می‌دهند و با این یادداشت خوانده می‌شوند.

این جدول انتخاب معماری پیشنهاد می‌کند. patch نسخه‌ها در آغاز ساخت از منابع رسمی کنترل و در فایل قفل و image digest ثبت می‌شود؛ هیچ وابستگی شناور latest در انتشار نیست. React و ابزار CSS باید با نسخهٔ Next انتخابی سازگار قفل شوند.

## چرایی دیتابیس

فروش، سفارش، پرداخت، سهم مرکز و بلیط رابطهٔ دقیق دارند. PostgreSQL را مرجع قطعی این داده‌ها می‌گیریم. قفل‌کردن ردیفِ از پیش موجود صندلیِ سانس و قید یکتا، تصمیم فروش را در خود دیتابیس محافظت می‌کند. حافظهٔ مرورگر، کش یا پیام رسانده‌شده به سایت دیگر مجوز فروش نیست.

PostgreSQL سازوکار قفل ردیف را مستند کرده است؛ الگوریتم و آزمون ما باید از آن درست استفاده کنند. [قفل‌های PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html)

## چرایی بک‌اند

پیشنهاد Django به نیاز پنل، کاربران، مجوز، مهاجرت و نگهداری پکیج مربوط است. FastAPI نیز برای API مناسب است، اما برای این محصول به اجزای بیشتری برای مدیریت و مجوز نیاز خواهیم داشت. NestJS گزینهٔ تیم تمام TypeScript است؛ مزیت آن وحدت زبان و هزینهٔ آن بازنویسی قواعد Python است. کد فعلی به‌تنهایی انتخاب Django را قطعی نمی‌کند.

Django 5.2 شاخهٔ LTS است و Python 3.13 را پشتیبانی می‌کند. برنامهٔ ارتقا باید پیش از پایان پشتیبانی تنظیم شود. [نسخه‌های پشتیبانی‌شده](https://www.djangoproject.com/download/)؛ [سازگاری Python](https://docs.djangoproject.com/en/5.2/releases/5.2/)؛ [سازگاری DRF](https://www.django-rest-framework.org/community/3.16-announcement/)

## چرایی فرانت‌اند

صفحات فیلم، سینما و سانس برای اشتراک‌گذاری و جست‌وجو مهم‌اند؛ Next.js برای صفحات عمومی و React برای نقشهٔ صندلی و پنل‌ها انتخاب پیشنهادی است. تمام قواعد مالی و تصمیم فروش فقط در Django می‌ماند.

گزینهٔ ساده‌تر، قالب‌های Django با تعامل JavaScript محدود است: یک runtime کمتر و نصب ساده‌تر، اما برای نقشه و پنل‌های تعاملی به طراحی متفاوت نیاز دارد. اگر اولویت اصلی کاهش هزینهٔ نگهداری باشد، این جایگزین باید پیش از بستن A04 بررسی شود.

Next.js مستقل از میزبان خاص قابل استقرار است؛ برای نصب مستقل، پراکسی جلوی آن قرار می‌گیرد. [استقرار مستقل](https://nextjs.org/docs/app/guides/self-hosting)؛ [سیاست پشتیبانی](https://nextjs.org/support-policy)

## اجزای گزینهٔ Next.js و broker مستقل

~~~mermaid
flowchart LR
    U["مرورگر"] --> N["Nginx / HTTPS"]
    N --> W["Next.js: سایت و پنل"]
    N --> B["Django: API / callback"]
    W --> B
    B --> P[("PostgreSQL")]
    O["ناشر Outbox"] --> P
    O --> Q["RabbitMQ"]
    Q --> C["Celery worker"]
    C --> P
    C --> E["درگاه / پیامک / مرجع بیرونی"]
    B --> E
~~~

تماس بیرونی داخل تراکنش باز دیتابیس انجام نمی‌شود. نتیجهٔ نامشخص با شناسهٔ عملیات ماندگار پیگیری می‌شود. فرایند وب، worker و ناشر از یک کدبیس بک‌اند ساخته می‌شوند؛ این‌ها به معنی چند میکروسرویس کسب‌وکاری نیستند.

در گزینهٔ سبک، Nginx به Django و دارایی‌های static هدایت می‌کند، worker با PostgreSQL کار می‌کند و Next.js/RabbitMQ در اجرای عملیاتی لازم نیستند. هیچ‌کدام هنوز انتخاب نهایی نیستند.

## ماژول‌ها

identity، organizations، catalog، cinema، inventory، orders، payments، ticketing، finance، support، integrations، notifications، audit، operations و site_settings.

ماژول سینما تعریف فیلم، سالن، نقشه و سانس را مالک است؛ inventory به شناسهٔ موجودی و صندلی وابسته است، نه جزئیات فیلم. پکیج‌های آینده از همان مسیر سفارش، پرداخت و مالی استفاده می‌کنند. غیرفعال‌کردن پکیج دارای فروش، سوابق و بلیط‌ها را حذف نمی‌کند.

## حداقل استقلال مشتری

هر نصب دیتابیس، فایل‌ها، کلیدها، صف و backup مستقل دارد. یک نسخهٔ محصول برای همه، با تنظیمات و پکیج‌های متفاوت نصب می‌شود. خرابی سرویس تولیدکننده یا پایان پشتیبانی نباید استفادهٔ روزمره از نسخهٔ خریداری‌شده را متوقف کند.

این پیشنهاد هنوز هزینه یا ظرفیت تضمین نمی‌کند. سرور پایه پس از آزمون بار تعیین می‌شود.
