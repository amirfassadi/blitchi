# استقرار، امنیت و عملیات

وضعیت: طرح پیشنهادی؛ دستورات عملیاتی و پیکربندی نهایی در مرحلهٔ ساخت و آزمون تکمیل می‌شوند.

## مدل تحویل

پیشنهاد: استقرار مرجع روی سرور مستقل با Docker Compose؛ همان بسته می‌تواند توسط مشتری یا با قرارداد مدیریت‌شده اجرا شود. شکل قرارداد هنوز باید با مالک محصول تثبیت شود. اجرای هر دو مدل به معنی پشتیبانی از هر سیستم‌عامل و هر محیط نیست.

پیکربندی مرجع: Ubuntu 24.04 LTS، معماری x86_64 و Docker Engine/Compose سازگار. image و وابستگی‌ها با نسخه و digest مشخص منتشر می‌شوند. منابع سرور نتیجهٔ آزمون بار است؛ عدد حدسی به‌عنوان حداقل تضمینی فروخته نمی‌شود.

[سازگاری Docker با Ubuntu](https://docs.docker.com/engine/install/ubuntu/)

## گزینه‌های در حال بررسی

A04 و A06 تعیین می‌کنند Node و broker مستقل در اجرای محصول لازم‌اند یا نه. گزینهٔ سبک: Nginx، Django، worker و PostgreSQL؛ گزینهٔ قبلی: Next.js و Celery/RabbitMQ نیز اضافه می‌شوند. شرح broker و Next در ادامه برای گزینهٔ دوم است و الزام بدون تصمیم محسوب نمی‌شود.

## اجزا و شبکه

Nginx، Next.js، Django، Celery worker، یک scheduler/dispatcher، RabbitMQ و PostgreSQL. worker و scheduler از image یکسان backend هستند. تنها پورت HTTPS عمومی لازم است؛ HTTP برای redirect یا صدور گواهی مطابق تنظیمات. DB، broker و ابزار مدیریت شبکهٔ عمومی ندارند.

فقط /api/v1 و callbackها به Django، مسیرهای وب به Next و فایل‌های عمومی کنترل‌شده به storage هدایت می‌شوند. headerهای proxy تنها از پراکسی مورد اعتماد پذیرفته می‌شوند. هم‌مبدأبودن وب و API باعث یکپارچگی session می‌شود؛ CSRF همچنان لازم است.

سرور تکی نقطهٔ شکست دارد. backup خارج سرور و runbook بازیابی اجباری است؛ Compose به‌تنهایی HA یا تحمل خرابی دیتابیس ایجاد نمی‌کند.

## فایل و اسرار

- تنظیمات غیرحساس برند از دیتابیس یا فایل نصب؛ رمز و کلید از secretهای محیط نصب.
- فایل نمونه فقط placeholder خالی دارد؛ کلید واقعی، dump، فایل مشتری یا credential به git نمی‌رود.
- کلیدهای QR، امضای کانال و backup چرخهٔ ایجاد، نسخه، چرخش و ابطال دارند.
- فایل‌های عمومی و پیوست خصوصی storage و مجوز متفاوت دارند. URL پیوست خصوصی بدون مجوز دائمی عمومی نیست.
- محدودیت اندازه، نوع فایل، بررسی محتوا و جلوگیری از اجرای upload پیش از عرضه لازم‌اند.
- مشتری در پایان نصب مالک credentialهای خودش است؛ تولیدکننده بدون رضایت دسترسی دائم یا ارسال داده ندارد.

## صف و تداوم کار

RabbitMQ با ذخیرهٔ پایدار، محدودیت منابع، تأیید انتشار و ack مصرف راه‌اندازی می‌شود. یک node، خوشهٔ مقاوم نیست. DB Outbox مرجع بازسازی کارهای منتشرنشده است؛ سن پیام، lag و خطای ارسال پایش می‌شوند.

workerها task تکراری را تحمل می‌کنند. پس از restart، کارهای نیمه‌تمام query و lease منقضی بازیابی می‌شوند. ساعت scheduler باعث آزادسازی نامعتبر صندلی نمی‌شود؛ منطق زمان در مرجع تصمیم می‌گیرد.

## پشتیبان و بازیابی

PostgreSQL base backup و WAL archive برای هدف RPO پیشنهادی، به مخزن خارج از سرور و با رمزگذاری و retention تعریف‌شده فرستاده می‌شوند. backup فایل‌ها، پیکربندی، نسخهٔ برنامه و کلیدهای لازم نیز لازم است. داشتن فایل backup بدون تمرین restore پذیرش نیست.

runbook بازیابی: توقف پذیرش فروش ← بازیابی محیط و داده ← بازپخش رخدادهای قابل بازیابی ← تطبیق درگاه، مرجع موجودی، بلیط و دفتر مالی ← مسدودکردن موارد نامطمئن ← تأیید مسئول ← بازگشایی.

اگر بلیط‌چی مرجع موجودی است و بخشی از فروش از دست رفته، ظرفیت صرفاً به علت نبود سابقه آزاد فرض نمی‌شود. RPO پانزده‌دقیقه‌ای هدف زیرساخت است، نه اجازهٔ از دست دادن پول یا فروش مجدد صندلی.

## انتشار و ارتقا

CI: بررسی سبک، typecheck، تست واحد، PostgreSQL integration و concurrency، contract test، build وب و تست مرورگر. اسکن وابستگی و image و کنترل نسخه‌های پشتیبانی‌شده انجام می‌شود. شکست CI مانع انتشار است؛ bypass اضطراری با مسئول و دلیل ثبت می‌شود.

Artifact یکسان در staging و مشتری نصب می‌شود؛ build اختصاصی از fork مشتری ساخته نمی‌شود. مهاجرت نسخه‌دار و ترجیحاً expand/contract است. در v1 پنجرهٔ نگهداری کنترل‌شده، توقف رزرو جدید، مدیریت عملیات در جریان و دریافت ماندگار callback لازم است.

برگشت image با restore دیتابیس یکی نیست. پس از ثبت دادهٔ جدید، restore کور ممنوع است. هر release مسیر rollback یا forward-fix و ماتریس ارتقای آزموده‌شده دارد.

## پایش و هشدار

request_id، order_id، inventory_operation_id و provider_ref پوشانده‌شده برای ردیابی مرتبط‌اند. log بدون OTP، session، کلید و دادهٔ بانکی کامل ثبت می‌شود.

شاخص‌ها: latency و خطای رزرو، تعارض ظرفیت، سن Outbox، صف worker، تعداد و مبلغ پروندهٔ نامشخص، نزدیک‌بودن برنامه، خطای درگاه و پیامک، مغایرت مالی، فضای دیسک، اتصال DB و وضعیت backup.

هشدار عملیاتی باید مالک و کانال پاسخ داشته باشد. مسئول و جانشین قبل از پایلوت واقعی تعیین شوند؛ تولیدکننده بدون قرارداد مسئول شبانه‌روزی فرض نمی‌شود.

## دروازه‌های عرضه

۱. معماری و دامنهٔ پذیرفته‌شده.
۲. ارائه‌دهندهٔ واقعی پرداخت و موجودی آزموده‌شده.
۳. D14 و قراردادهای لازم تکمیل‌شده.
۴. احراز هویت و مجوز و کنترل ورود با زمان واقعی.
۵. آزمون بار و پروتکل ۱۶.۵، گزارش restore و تطبیق.
۶. راهنمای نصب، ارتقا، پشتیبان و پاسخ به رخداد.
۷. پایلوت یک سینما و یک دورهٔ تطبیق و تسویه.
۸. تأیید مسئول عملیاتی و محدودهٔ اعلامی محصول.

هیچ‌کدام از این موارد با داشتن ۲۵ تست نمونهٔ SQLite اثبات نشده‌اند.

## پیش‌نیاز شبکه و رفتار محلی

W005 و T43 باید دسترسی میزبان واقعی به registry imageها، PyPI و در صورت نیاز npm را بررسی کنند؛ بازبودن اینترنت فرض نیست. اگر محدودیت وجود داشت، image و wheel/asset از مسیر مجاز یا بستهٔ آفلاین دارای manifest و digest تهیه شود. نصب نباید مخفیانه registry ناشناس یا mirror تأییدنشده را معتبر بداند.

رفتار verify و برگشت خودکار درگاه خاص مطابق مدارک همان provider در W020/T47 ثبت می‌شود، نه با تعمیم «همهٔ درگاه‌های ایرانی». این سند دربارهٔ مقررات یا رفتار درگاه نامشخص حکم قطعی نمی‌دهد.

## مالک تصمیم‌های عملیاتی

A13 امضا، A14 MFA، A15 rate limit، A16 backup، A17 پایش و A21 توزیع بسته پیش از عرضهٔ قابلیت مربوط باید بسته شوند. نام ابزار و credential واقعی هنوز خالی است.
